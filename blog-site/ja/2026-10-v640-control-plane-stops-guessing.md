# v6.4.0：推測しないコントロールプレーン——台帳は分岐しない、拒否は機能、ゲートは宣言どおりの場所で走る

> **TL;DR:** 今回のテーマは「推測しない」です。計画台帳は同じ作業項目を二重に登録すると静かに 2 つのドキュメントに分岐でき、能力アクティベーションを持つのは片方だけでした。`aios plan` は書き込み要求に読み取り専用ビューを渡して exit 0 で終わりました。宣言されたチェック（ディレクトリ予算、スキル変更の影響テスト選択）はディスクには存在しても CI では一度も走りませんでした。v6.4.0 はそれぞれを釘付けにします。A21 は計画ターンがアクティブな台帳を再利用し、A22 は作業項目に正規のアイデンティティを与え、A23 はそのアイデンティティを Capability Command のバインディングまで伝播させます。A19 は未実装のサブコマンドを `status` に置き換える代わりに拒否し、A20 はトレーニングゲートが検証ベースと各拒否の補救を語ります。同じリリースで ADR 0003 の落とし先三問に従い mattpocock/skills v1.3 のトリオを両面で採用しました。親リポジトリに `retro` と `implement-spec` が加わり、rex-harness 0.11.0 はスタンドアロン向けオーケストレーションスキル `rex-implement-spec` / `rex-pr` / `rex-retro` を出荷します。インストール投影は 14 から 17 へ増えます。

## 台帳は分岐しない（A21 → A22 → A23）

この一線は、同じ病巣の 3 つの顕在化を直します。**計画台帳は「どのドキュメントがアクティブか」で答え、同じ作業項目を二重に登録すると 2 つ作れてしまう。**

A21 がまず再利用を直します。`workflow-policy.mjs` は「計画ターンは必ず新しい台帳を作る」とハードコードしており、同じ項目を 2 回登録すると（`plan start` の後に `plan auto-gate`）、`-2` 接尾辞だけで違う 2 つのドキュメントができ、能力アクティベーションを持つのは新しい方だけでした。アクティブな計画に作用する `plan task` や `plan add-evidence` は、最初の台帳を静的に孤児化します。再利用は状態事実（アクティブで未終端の計画が存在する）でキーされ、目的テキストの類似性では決してキーされません。宣言された逃げ道は `plan auto-gate --new-work-item` で、`strict` モードも再利用します。strict とは「常に台帳から作業する」であって「毎ターン鋳造する」ではないからです。

A22 がアイデンティティを追加します。`plan start --work-item <id>` は作業項目に正規のアイデンティティを与えます（大文字小文字・空白・句読点を正規化し、`..`・パス区切り・制御文字を拒否）。アイデンティティは**宣言**され、決して推測されません。既存の id はその台帳を再アクティベートし、ストアを失ってもドキュメントが生きていれば再養子縁組（`recovered: true`）します。別の `-2` を鋳造するのではなく。ガードは私たちが予想していなかった穴を捕まえました。宣言したのに空の `--work-item ""` は「フラグ不在」に折りたたまれて無キーパスに落ち、この機能が防ぐために存在する兄弟台帳をちょうど鋳造してしまう——アイデンティティは存在性で判定され、空の宣言は拒否されます。

A23 が伝播を閉じます。A22 が `plan start` にアイデンティティを与えても、計画ターンの台帳を書くゲートは依然として何も渡しませんでした。ゲートが鋳造した台帳は `workItemId: ''` のままで、rex のアクティベーションはパスかターンごとのハッシュでキーされていた——台帳はある id に答え、完了を認める Command は別のものに答えていました。アクティベーションキーは現在、順序付きの優先順位です。宣言 id、次に台帳パス、次にターンハッシュ。id→パスの読み通し付きで、A23 以前のパスキー方式のアクティベーションも到達可能のままです。2 つの優先規則は設計ではなく実測から来ています。宣言 id の正規形がアクティブな計画の id と**異なる**場合は独自の台帳を作る（A21 の再利用が明示的に異なる宣言を呑み込んではならない）。`--work-item X --new-work-item` は優先順位で解決するのではなく exit 1 で拒否される。この組み合わせはアクティベーションキーが衝突する 2 つ目の台帳を書くからです。直感に反する釘を一本。`canonicalizeWorkItemId('')` は `''` を返さなければなりません。共有 slugify は空入力に対してリテラルの `'plan'` にフォールバックし、それが宣言のないすべてのターンを「別の作業項目」に見せて A21 の再利用を静的にオフにしていたからです（原因が見つかるまで 5 つのテストが失敗しました）。

## 拒否は機能（A19）

`aios plan` は 2 つの静かな置き換えで台帳を書き込み不能にしていました。argv パーサーは**あらゆる**未実装のサブコマンドを `status` に書き換え（だから `plan list` も、タイプミスした `plan setstatus` も、計画を表示して exit 0）、`status` ブランチは `--status/--note/--force` を無視しました（だから `plan status --status done` は何も変えずに exit 0）。2026-09-21 に完了した作業項目はそれゆえ 3 週間 `executing` のままでした——そして陳腐な `executing` 計画こそ、すべての「継続」再開が信頼するものです。台帳は次のセッションを能動的に誤導していました。

修正は fail-closed で進みます。パーサーは宣言されたサブコマンドを逐語的に通し、語彙のコピーを所有するのをやめる。ブランチ集合を所有する ops レイヤーが `PLAN_SUBCOMMANDS` をエクスポートし、未実装の名前を有効なものを列挙しながら拒否する。`status` は書き込みフラグを拒否し `plan set-status` を指す。ヘルプはついに `aios plan set-status …` を宣伝する——この行の欠落こそ罠が生き延びられた理由です。2 つの変異は独立して捕まります。パーサーフォールバックの再導入は C2 だけが失敗し、`status` ガードの削除は C3 だけが失敗します。

## ゲートは宣言どおりの場所で走る（A20 + ディレクトリ予算 + 影響テスト）

**A20 — トレーニングゲートが検証ベースを語る。** `verify-training` は 9 種類の失敗を 1 つの文に圧縮していたため、**間違ったベース**で記録された証明書は陳腐なコンテンツと同じに見えました——しかし補救は異なります。拒否された各エントリは `code` + `reasonKind` + `remedy`（正確なコマンド）を運び、改ざんされたベースライン成果物と別ベースで記録された証明書は 2 つのブランチに分かれ、PowerShell 側のプレフライトは失敗時に出力を飲み込む代わりに再フローします。

**ディレクトリ予算 — ルールが CI で走る。** AGENTS.md は「ディレクトリあたり最大 8 エントリ」を宣言し、`check-dir-budget.mjs` は阻塞違反で確かに exit 1 します——しかし実行面がゼロでした。`package.json` にも、ワークフローにも、pre-commit にもなく、リポジトリは 2 つの阻塞違反に漂移しながら全スイートは緑のままでした。現在は `pretest:scripts` の第 2 ステップとして走ります。CI（とリリース）は新しい超過ディレクトリで失敗します。漂移した 2 ディレクトリはまずスクリプトのラチェットベースラインに凍結され、意味的な分割は別項目です。

**影響テスト — スキル変更が静かに 0 テストを選ばない。** 今サイクルで実測：`skill-sources/retro/SKILL.md` を含む 8 ファイルの変更で、セレクターは「選択 0/219」と表示しました。skill-sources のファイルはガードスイートがディレクトリ走査で読み、import では決して読まれないため、静的影響グラフに辺がなかったのです。任意の `skill-sources/` 変更は現在スキルガード接頭辞に帰属し、13 のガードテストが選ばれます。

## セッションから環境へのループ（トリオ両面 + A16）

このリリースはある質問にも答えます。**レトロスペクティブで出た環境の教訓は、どこに着地するのか。**

親リポジトリは ADR 0003 の落とし先三問に従って mattpocock/skills v1.3 の `retro` と `implement-spec` を採用します。`retro` はセッションを「コードではなく環境を変える」候補について 7 カテゴリ（ナビゲーションポインタ、決定論的チェック、コーディング標準、AGENTS.md の追加削除、ツール経済性、無効な指示、情報の到達性）で振り返ります。提案のみ、ファイル書き込みは決してなし、すべての候補にソース参照が必須、7 カテゴリそれぞれが「未見」を accounting する。`implement-spec` は受け入れ基準と作業項目グラフを既に持つ spec の実行エントリです。フロンティアを取り、承認された `aios work` ゲートを通じて並列ディスパッチし、統合ブランチで閉じ、`/review` で仕上げる。

スタンドアロンの rex-harness ユーザーはどちらも持たないため、rex-harness 0.11.0 は framework-free のオーケストレーションスキル `rex-implement-spec` / `rex-pr` / `rex-retro` を出荷します。Provider ではなく Capability Command に選ばれることもなく、`rex-workflow` と同じオーケストレーション面を共有します。スタンドアロンインストール投影は 14 から 17 へ。両面配置は `grill` ↔ `rex-requirements` と同じ先行例に従います。

最後に、オペレーター承認のクリーンアップです。リポジトリ全体でインポーターがゼロの「コアインフラバレル」を自称していた `src/core/index.mjs` が削除されました（登録 A16 閉鎖）。ヘッダーが描くエントリポイントとして採用するのは、機能的便益のないリポジトリ全体の import パス書き換えを意味します。必要になった時に再構築する方が、デッドコードを維持するより安い。

## アップグレードノート

- 破壊的な移行はありません。更新後に `aios init` を再実行（またはスキルを再同期）すれば、新しい `retro` / `implement-spec` スキルが手に入ります。
- rex-harness ポインタは 0.11.0 に進みます。スタンドアロンのみのユーザーは投影されるオーケストレーションスキルが 3 つ増えますが、既存の挙動変更はありません。
- 本リリースのトレーニング証拠は v6.3.0 ベースに対して再発行されました（決定論的・ローカル・モデル不介入）。ワークスペースに独自のスキル変更がある場合は、タグ付け前に同じ補救を実行してください。`aios skill certify --changed --base v6.3.0`。
