# 我们实测了自己的 token 压缩：AIOS Token Bench 首份 A/B 数据

> **一句话答案：** 我们不再争论"压缩到底省不省"，改为直接测量。在冻结的 8 任务基准上（模型钉死），我们对新上线的 Pi 观察卸载机制（关 → 开）跑了三对 A/B。token 节省在前两对是 +16% 和 +21%，第三对**反转成 −64%**——三对平均 −4%——原因是模型有时在大读取任务上多花很多轮翻页取回。成本均值省 21%，方差同样大。所以诚实的标题是：目标任务常常能省一半 token，机制按我们自己立的两道闸门**以 opt-in 发布（默认关闭）**，方差是下一个工程问题。以下每个数字都能用三条命令复现。

## 为什么是测量，不是争论

NVIDIA 的 SoL-Pi 用自动研究循环加冻结的 held-out 基准，把 152 个候选机制筛到 4 个。我们评估了他们的包，发现与我们 Pi 安全闸门和托管传输有两个结构性冲突，最终一行没装——但把那套纪律整体借了过来：

1. **冻结任务集**：只做验收，永不用于调参。
2. **统一账本**：每个 token 事件都归属到层、任务和模型。
3. **两道验收闸门**：能力检查必须通过、实测节省必须为正——否则机制保持 opt-in。

## 基准长什么样

AIOS token bench 就在仓库里：8 条冻结任务（纯回复、JSON 契约、shell 往返、小/大日志读取、多轮写后跑），打托管 Pi RPC 传输执行，模型钉死在 `kimi-k2.7-code`。每一轮的用量——输入、输出、缓存读、成本、停止原因——都按任务 id 流进账本。

```bash
node scripts/token-bench/run.mjs --dry --json   # 校验冻结集，不启动任何客户端
node scripts/token-bench/run.mjs --session bench-ab-off --model <provider/model>   # 实跑，烧真实 token
node scripts/token-bench/compare.mjs --a bench-ab-off --b bench-ab-on              # A/B 对比报表
```

## 首份 A/B 结果

同一批任务、同一个模型，唯一的变量：观察卸载机制关 vs 开。这是三对中的第一对。

| 任务 | 关·轮次 | 开·轮次 | 关·tokens | 开·tokens | Δ tokens |
| --- | --- | --- | --- | --- | --- |
| bench-001 纯回复 | 1 | 1 | 16,548 | 16,559 | +11 |
| bench-002 shell 版本号 | 2 | 2 | 33,210 | 33,229 | +19 |
| bench-003 小日志读取 | 2 | 2 | 33,531 | 33,787 | +256 |
| bench-004 数 ERROR 行 | 3 | 2 | 53,465 | 35,070 | −18,395（−34%） |
| bench-005 JSON 契约 | 1 | 1 | 16,566 | 16,578 | +12 |
| bench-006 算术命令 | 2 | 2 | 33,254 | 33,239 | −15 |
| bench-007 大日志读取（126 KB） | 4 | 2 | 67,500 | 34,316 | −33,184（−49%） |
| bench-008 多轮写+跑 | 3 | 3 | 50,272 | 51,570 | +1,298（+3%） |
| **合计** | | | **304,346（$0.1035）** | **254,348（$0.0602）** | **−49,998（−16%）** |

## 这些数字真正说了什么

**目标形状的反应和设计完全一致。**bench-007 强制把约 126 KB 的工具观察塞进上下文。机制开启后，这份观察只落盘一次、上下文里只留句柄加摘要，模型只在需要时精确翻页取回。该任务 token 降 49%，轮次从 4 轮收敛到 2 轮。

**成本降得比 token 快。**总 token 降 16%，实测成本降 42%。关臂多出来的轮次在按最贵的价格重复计费大块未缓存输入；轮次变少后，更多消耗转移到缓存读上。优化 token 能拿到一部分，优化轮次才能拿全。

**小任务是噪声带，这本身就是结论。**零工具任务背着约 16K token 的上下文地板（系统提示加 harness 基线），任何卸载机制都碰不到它——我们更早的基线里这个地板占总消耗 59%。卸载不是治地板的杠杆，地板数字的存在意义就是把这个边界说清楚。

## 另外两对显示了什么

我们承诺过 default-on 决策之前跑满三对重复。它们改写了故事：

| 配对 | 关·tokens | 开·tokens | Δ tokens | Δ 成本 | bench-007 关 → 开 |
| --- | --- | --- | --- | --- | --- |
| 1 | 304,346（$0.1035） | 254,348（$0.0602） | −16% | −42% | 67,500 → 34,316（4→2 轮） |
| 2 | 338,064（$0.0982） | 268,559（$0.0585） | −21% | −40% | 120,284 → 67,432 |
| 3 | 237,685（$0.0551） | 389,675（$0.0837） | **+64%** | **+52%** | 36,240 → 172,992（10 轮） |
| **均值** | 293,365 | 304,194 | **−4%** | **−21%** | |

第三对反转了。逐轮账本把原因指得清清楚楚：开臂的 bench-007 跑了 **10 轮而不是 2–4 轮**，每一轮成本结构都正常（同样的 ~16K 地板、缓存读健康）——模型反复翻页取回，迟迟不肯收敛。机制没有故障；恰恰在机制针对的那类任务上，模型的取回策略是高方差的。

由此得出两个诚实结论。其一，三对里成本均值仍省 21%，且模型快速收敛的两对中机制表现与设计一致——但 token 均值 −4% 不是稳定的赢。其二，按我们自己立的两道闸门，**机制以 opt-in 发布（默认关闭，`AIOS_PI_OFFLOAD=on` 显式开启）**，直到方差有了工程答案：给每个任务设取回预算，超预算后句柄退化为"归档过大"的普通指针。

## 我们仍然不声明什么

- **均值不是稳定的赢。**三对 −4% 的 token 均值在零的方差范围内；成本均值（−21%）好一些，但靠的是同样三次掷骰子。
- **ON 臂有一次检查失败**（第一对开臂的 bench-007 回复漏掉期望 id）。同机制同模型单独复跑时精确命中。我们判定为模型方差而非机制损伤——但它记录在案，不是"偶发、忽略"。
- **token 数字来自运行时的 usage 上报**，不是厂商账单。下文三个月账本的数字是字节估算（bytes ÷ 4）。
- **只有一个模型。**换后端，百分比可能明显移动——包括取回轮次方差本身。

## 背后的三个月账本

A/B 是新的，记账不是。refs 层——在编排器边界卸载超大工具输出的那层——从六月起记录每个事件。截至本文：**2,552 个事件，估算 raw 5.73M tokens，5.43M 没有进入上下文（94.8%）**，零失控事件、零策略违规。大头是 MCP 工具结果（1,768 个事件）和工具清单（578 个）。`aios tokens report` 按层、按会话打印这些。

## 机制本身，一段话说完

`ObservationPack-lite` 随 AIOS Pi 扩展发布，**默认关闭**（`AIOS_PI_OFFLOAD=on` 显式开启）。在 Pi 的 `context` 事件（每次 LLM 调用前触发）上，任何达到 20K 字符的文本观察会被一次性归档到工作区状态根下的内容寻址文件，上下文里的副本替换为一个 16 位十六进制 ref、行数/字节数和头尾摘要。只读的 `aios_offload_retrieve` 工具按 ref 和行区间翻页取回原文。它不碰工具执行，所以与安全闸门零交互。

## 往后的规矩

任何机制默认开启之前，必须过冻结基准上的两道闸门：能力落在容差内、节省实测为正——而且是跨重复对稳定成立，不是一次好运。ObservationPack-lite 在它的取回轮次方差有了工程答案之前保持 opt-in（显而易见的候选方案是给每个任务设取回预算，而基准存在的意义正是验证它）。基准从真实任务历史里持续扩充，账本保存凭证，从这篇开始，博客上的每个声明都应该是一条别人能跑的命令。
